# Agent 自动化反馈闭环

## 给用户的反馈

开始时简短说明正在处理的工程、范围、成功标准和覆盖策略，不复述一长串命令。执行中在有意义的节点反馈：发现了什么、当前哪轨/哪段、采取何种修改、校验是否改善、下一步要消除什么不确定性。耗时任务约每分钟仍应有简短进度；状态不变时不要重复刷屏，不编造百分比或完成时间。

渲染 stderr 提供 JSON `render_progress`（轨名、完成/总数、状态、错误），worker 还有 loading/warmup/native_single_pass/coverage 事件。读取现有任务可用：

```sh
sv2cli job-status stems
sv2cli job-status mix.wav
```

最终结论说明当前交付路径、实际改善和剩余具体问题。不要把“准备做”“工具通过”写成“已听过且满意”。

## 给自动化步骤的反馈

在用户工程的工作目录写一个任务内 `workflow-feedback.json`，包含当前目标、约束、用户反馈、局部问题和迭代记录。它是本次任务记录，不是修改全局长期记忆；不向公开仓库提交。

建议字段：`goal`、`constraints`、`userFeedback`、`issues`、`iterations`。每个问题记录 track/reference/bar 或秒数、用户描述、测量依据、期望结果；每轮记录输入标识、具体操作、before/after 数值、输出文件、判定和下一步。与工程/音频哈希关联，避免把上一轮报告用于新产物。

例如用户说“低声部接主旋律后还被伴唱盖住”，把它记成该段局部主次问题，核对谱面角色、力度和同时间窗能量；不要把整个作品永久改成低音最大。用户已经纠正过的方向优先进入下一轮约束，不能继续重复被否定的处理。

## 基于原因的修复与验证

读取当前产物并定位问题，记录证据的范围。依据原因修改工程、配置或代码，并保留原始结果。新版本只渲染一次，再比较同一时间轴和同一指标。无修改时不得继续重渲染，不能按误差、覆盖率或“连续两次稳定”挑选结果。固定数量的宿主诊断对照可用于查因，不能将其中幸运通过的一次作为生产产物。

短音不能从活动检查中略过；检查 coverage-check 的 missingWindows 与 unexpectedSilence。合法休止不算漏声，混音中的其他轨会掩盖缺失，故逐声部验收仍需独立分轨。宽频能量与有声能量只选有明确声学理由的标记，不能自动换阈值或标记直到通过。

程序性通过不能替代主观反馈。只有用户实际试听后表达接受，才能记录 userAccepted；没有回复不算接受。可测延迟已改善、但连唱或音素仍未测时，分别记录，不把局部改善推广成全曲对齐。
